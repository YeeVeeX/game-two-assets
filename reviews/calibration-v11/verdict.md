what a press landing one tick late produces and it is also clean, so the
boundary-turn class is robust to ±1 tick of input timing.** That robustness,
not CORNER's marginal smoothness, is the decision-relevant result.

**Recommendations recorded for the future runtime-replay integration design
(game-two decisions for AFTER the cycle closes; never implemented from here,
never compensated with pixels):**

- **REM-gating / boundary buffering is now the primary recommendation, and
  frame selection is DEMOTED to a footnote.** Rendered evidence: the turn is
  clean at REM 0 (CORNER, this sprint) and at REM ≤ 4 (v10 LATE, where the
  strafe is settle-only *because the banked mapping already draws f3 there*),
  and it fails at REM ≥ 8 under BOTH treatments measured — cycling gait
  (v10, moonwalk) and held settle frame (v11, dead drag). Since the
  settle-hold substitution is a no-op precisely in the regime that already
  passes, it cannot be the remedy for the regime that fails.
- **If frame selection is pursued anyway, the rework must add motion, not
  remove it** — e.g. a 2-frame settle bob, or a dedicated side-step/strafe
  pair. The latter is the only option that would put pixels back on this
  repo's plate, and nothing in this sprint asks for it yet: gating removes
  the need.
- **Facing-lock during the tween** (the v9 alternative, ~217 ms worst-case
  turn latency) remains the other structurally complete answer: it deletes
  perpendicular travel instead of trying to draw it.
- **NEW implementation duty (council Q4):** a buffered-turn implementation
  must define diagonal input handling — `held_direction` returns `[1,1]` on
  a 1-tick key overlap, `face` accepts it, the notch already draws a corner

  second press) rather than inherit a facing the art cannot draw.
