# Sprint 0 — silhouette calibration

## Problem

A toolchain-only sample can prove that Aseprite exports a PNG, but it cannot answer the expensive question: which visual language keeps the game readable at 32x32 while improving the current rectangle bodies?

For example, a detailed concept may look strong at 4x and disappear against ZONE 1 at native scale. Producing a full cast before testing that failure would create decorative inventory, not usable assets.

## Solution

Compare **three silhouette languages for the same generic body**. Hold role color, canvas, pose, and background constant so the review isolates shape language rather than character content.

- **Lane A — geometric lineage:** evolves the current hard rectangle/notch language; strongest continuity and lowest engine risk.
- **Lane B — compact bodily form:** clearer head/torso/feet grouping with restrained 16-bit-style clusters.
- **Lane C — asymmetric action form:** one deliberate directional mass that tests facing and attack readability without overhang.

These are functional lanes, not fiction concepts. Cite the current renderer, the KB technical-drawing/pixel-workflow notes, Tibia footage research for grid readability, and Vlambeer material for action feedback. Extract principles; do not copy imagery.

## Scope

Produce, at most:

- one generic player body per lane;
- idle-down and idle-right poses for each lane;
- one optional attack-key pose only if idle facing is already legible;
- one deterministic contact sheet using current ZONE 1 and ZONE 2 palette samples;
- one release manifest and one saved verdict.

Bedrock may be used for high-resolution **shape reference only**. A general-model result is never an export. Reconstruct selected forms manually at native resolution in Aseprite.

## Evaluation rubric

### Accuracy — all must pass

- 32x32 RGBA8; hard alpha; declared palette; at most eight opaque colors
- occupied pixels remain within `[2,2,29,29]`
- source/export hashes and provenance validate
- contact sheet is generated by a script, not assembled by hand
- no game-two file changes

### Presentation — blocking

At native 1x, without reading a label:

- foreground separates from both tested floor/wall palettes;
- down versus right facing is immediately distinguishable;
- the possession ring remains visually dominant when applied;
- silhouette does not compete with telegraph red or transition gold;
- form remains coherent during a one-tile nearest-neighbor translation;
- no isolated-pixel noise or detail that exists only at magnified scale.

Score accuracy and presentation separately. A technically valid candidate can still be rejected.

## Process

1. Query `hub kb --domain game-research` before choosing shapes.
2. Capture the exact baseline and verify it against `../game-two`.
3. Write the three-lane rationale before generating candidates.
4. Author/reconstruct native candidates and export deterministically.
5. Run unit tests and `tools/asset_gate.py`.
6. Generate one contact sheet with 1x runtime rows and 2x/4x diagnostic rows.
7. Run structured vision critique, then one cross-vendor taste review.
8. Bank a verdict: one winner, or reject all with one concrete next hypothesis.

## Stop conditions

Stop after the first reviewed contact sheet. Do not create terrain, UI, enemies, animation sets, or a full player pack. Continue only if one lane passes every accuracy item and the presentation verdict identifies it as a real improvement over the primitive baseline. Do not touch game-two even if a lane wins; integration remains blocked until v17 closes.
